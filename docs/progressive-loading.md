# 段階読み込みとバックヤード訪問

Web版では、入口ページ → 操作できる簡易展示室と軽量模型 → 室内の形状・質感と選んだ標本の詳細、の順に読み込みます。2026年11月7日にローカルWebビルドとChromeで検証しました。公開サイトへの反映は別工程です。[室内データの分割と遅延ロード](room-streaming.md)も参照してください。

## 来館者の操作

- 入室前に、おおよその初回ダウンロード量を表示します。入室ボタンを押すまではUnity本体や詳細模型を先読みしません。
- 室内には輪郭・色・材質を残した軽量模型を表示します。標本を手に取ると、その1点の詳細メッシュを追加取得します。読み込み中も回転でき、完了時に向き・倍率を保って置き換えます。
- 詳細メッシュの取得が完了した展示標本は、展示台の模型にも同じメッシュを適用します。台上の位置・向き・大きさを保ち、その見学中は詳細模型を保持します。棚・顕微鏡・什器・案内役の形状と室内画像も、取得したものから置き換わります。
- 通信失敗時は簡易模型を維持し、「詳細を再取得」で再試行できます。「戻る」や別の標本の選択で保留中の取得を中断します。
- 画面上部の隅にある半透明の「バックヤード」から、未展示の25点をサムネイルで総覧できます。昆虫14点、化石5点、土器・石器6点を絞り込み、ページ送りして選べます。
- バックヤードの観察から戻ると一覧を再表示します。観察済みには同じセッション内でチェックを付けます。展示室での位置と選択を保ち、ストックを室内の移動先や自動見学へ追加しません。

## 容量の実測

MBは1,000,000 bytesです。HTTPヘッダーなどを除く生成ファイルの実サイズで、UnityのBuildReport上の合計値とは区別します。

| 対象 | サイズ |
|---|---:|
| 変更前の公開ファイル合計（23点、一括読み込み） | 46.59 MB |
| 段階読み込み導入時の起動用ファイル等 | 26.96 MB |
| コード・圧縮・フォント最適化後の起動用ファイル等 | 16.70 MB |
| 室内データを遅延ロードにした後の起動用ファイル等 | 6.95 MB |
| うちUnity `.data.unityweb` | 2.39 MB |
| うちWasm（エンジンとアプリコード） | 4.34 MB |
| 入室後に取得する室内の形状・質感16組 | 15.43 MB |
| 詳細模型48点の追加データ合計 | 11.12 MB |
| 1点の詳細模型の最大値 | 0.48 MB |

ストック25点を追加しても、一括読み込みの公開版と比べて起動前の必須データは約85％削減しました。直前の16.70 MBからは約58％削減です。室内16組は入室後に順次取得しますが、詳細標本48点は全点を観察しない限り全量を取得しません。キャッシュから追い出された後の再訪では再取得する場合があります。

初回6.95 MBの転送時間は、一定の実効速度が5 Mbpsなら約11秒、1 Mbpsなら約56秒です。接続待ち・解凍・Unity起動の時間は別です。依然として低速回線で即時起動できる容量ではありません。[容量最適化の調査](web-optimization.md)も参照してください。

起動用と室内データを合計すると約22.39 MBで、直前の16.70 MBより増えています。Web用LZ4バンドルは初期データのBrotliとは圧縮率が異なります。全室完成までの通信量削減ではなく、先に操作を始められる改善です。詳細標本の通信量はこの合計とは別です。

## ビルドとデータの分離

`MuseumProgressiveBuild.Prepare()` は現行23点とストック25点から、材質単位の統合メッシュを生成します。室内用は部品ごとの頂点クラスタリングで簡略化し、詳細用は元の頂点を保持します。メッシュだけを個別のLZ4 AssetBundleにするため、シェーダーや共通材質を各バンドルへ重複同梱しません。

生成先 `Assets/Museum/GeneratedWeb/` と `Library/MuseumWebBundles/` はGit対象外です。元のFBX、材質、編集シーン、GUIDは保持します。Webのビルド用シーンコピーだけで参照を軽量版へ置換し、ストックの元カタログ参照も外します。詳細模型48点の元FBX・詳細メッシュが起動用データに含まれないことをDetailedBuildReportで確認済みです。

`Museum → Web → Build GitHub Pages` は準備・ビルド・配信用ファイルの仕上げを行います。CLIの `build run` を直接使う場合は、先に `MuseumProgressiveBuild.Prepare()` を実行してください。入力が変わったまま古い生成物を使うビルドは停止します。

表面テクスチャにはWebGL専用の最大512px設定を使用します。色はRGB24、法線はRGBA32、Rチャンネルを参照する粗さ・高さはR8で、デスクトップ専用の圧縮テクスチャ形式に依存しません。原画像と他プラットフォームの設定は保持します。バックヤードのサムネイルは128pxずつのアトラスにまとめ、独立した高解像度模型のロードを伴いません。

配信用の `Content/` にハッシュ付きバンドルと `catalog.json` を出力します。公開スクリプトはファイル名・存在・バイト数を照合します。独立ドメインでもサブディレクトリでも、現在のページからの相対URLで動作します。

## キャッシュとメモリ

- サービスワーカーは入口のHTML・CSS・SVG・Webマニフェストだけをインストール時に保存します。Unity本体や詳細模型の全件プリフェッチはしません。
- 入口はネットワーク優先、通信失敗時はキャッシュを使用します。Unity初期データはUnityのデータキャッシュに任せ、SWへ二重保存しません。
- 詳細模型はハッシュ付きURLで、SWのCache Storageに最大8件、1件4 MiB以下を保存します。古い取得分から削除します。キャッシュが利用できない場合も通常の通信を継続します。
- 展示台へ反映した詳細メッシュは、その見学中は表示・観察で共有し、見学終了時に解放します。取得済みの展示点数に応じてメモリ使用量が増えます。バックヤードなど展示台のない標本の詳細バンドルは最大3点とし、最終使用順で解放します。
- ブラウザーが保存領域を消去した場合、再取得が必要です。入口のオフライン表示を確認していますが、全展示の完全オフライン動作を保証する仕様ではありません。

## 検証

Unity 6000.6.8f1のWebビルドはエラー・警告とも0件。Editorでは48点のカタログ、23点＋2か所の移動先、ストック25点すべての観察・復帰、メッシュ置換時の回転・倍率保持を確認しました。

Chromeのモバイルエミュレーション（390×844、360×640、640×360、DPR 1.5）では、実際のタップによるバックヤード起動・模型選択、分類、読み込み中の回転、503失敗と再取得、中断、メモリキャッシュでの再訪、ページ再読込後のSWキャッシュ利用、化石と土器の表示、8件のキャッシュ上限、オフライン入口を確認しました。未選択模型の通信が起きないこともHTTPサーバー側のログで検査しています。予期しないブラウザーエラーは0件でした。スマートフォン実機、Safari、Firefox、実回線の待ち時間・発熱は未検証です。

再実行用の検査は `work/test_progressive_web.cjs`（Node、Playwright、Chromeが必要）と `work/verify_progressive_editor.cs`（EditorのPlay中に `script eval --file`）です。Webテストは一時HTTPサーバーとブラウザーを終了時に閉じ、結果・画像を追跡対象外の `Temp/progressive-test/` に保存します。
